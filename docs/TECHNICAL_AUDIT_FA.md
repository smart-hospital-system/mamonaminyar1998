# بررسی فنی ASH Nexus HMS — خطاها، علت‌ها و راه اصلاح

تاریخ ممیزی اولیه: ۲۰۲۶-۱۰-۲۹

> یادداشت مرحلهٔ بعد: پس از این ممیزی، نسخهٔ پایهٔ ۰.۱ از صفر در همین مخزن ساخته شد. شرح نبود فایل‌ها در این سند مربوط به زمان شروع ممیزی است. برای وضعیت و محدودیت‌های فعلی، [راهنمای نصب و استفاده](SETUP_FA.md) را بخوانید.

## ۱. نتیجهٔ اصلی و حدود بررسی

**کد ارسال‌شده یک سیستم کامل و آمادهٔ استفادهٔ طبی نیست.** چند مانع اجرای قطعی، چند نقص امنیتی جدی و تعداد زیادی قابلیت پیاده‌نشده دارد. پیام `Generating...`، نام مدل‌ها، شمارنده‌های ابزار و عبارت `Build succeeded` به‌تنهایی گزارش خطای برنامه نیستند. در پیام شما traceback واقعی اجرای ویندوز وجود ندارد؛ پس نمی‌توان تعیین کرد در کمپیوتر شما دقیقاً کدام خطا اول رخ داده است.

در checkout فعلی پیش از این بررسی فقط این فایل‌ها وجود داشتند:

- `README.md`
- `LICENSE`
- `.gitignore`

فایل‌های `package.json`، `src/App.tsx`، `backend/app/main.py`، اسکریپت‌های PowerShell و تصاویر مذکور در مخزن حاضر نیستند. بنابراین ادعاهای قبلی دربارهٔ ساخت React، موفقیت build، ورود امن و تکمیل امکانات، **از این مخزن قابل تأیید نیستند**. محدودیت React-only نیز از فایل‌های فعلی اثبات نمی‌شود؛ داشتن یک frontend مانع افزودن backend واقعی نیست.

در این نوبت، کد فرستاده‌شده بررسی شد و بازتولیدهای مستقل حداقلی برای چند خطا اجرا شد. هیچ سیستم شفاخانهٔ عملیاتی نصب، راه‌اندازی یا کامل اصلاح نشده است. تصاویر دارای مسیرهای متنی در پیام، فایل تصویر قابل‌مشاهده در این checkout نیستند؛ دربارهٔ محتوای آن‌ها قضاوت نشده است.

## ۳. خطاهای دقیق و راه اصلاح

### الف) برخورد `models.py` با پکیج `models`

اسکریپت ۱ این فایل را می‌سازد:

```text
backend/app/models/__init__.py
```

اما اسکریپت ۲ مدل‌ها را اینجا می‌نویسد:

```text
backend/app/models.py
```

در بازتولید، import نام `models` به پکیج و `__init__.py` خالی رسید، نه به فایل حاوی `Base`.

**اصلاح:** یکی از دو ساختار را انتخاب کنید، نه هر دو. پیشنهاد بدون حذف عجولانهٔ اطلاعات:

```text
backend/app/models/
  __init__.py      # export مدل‌ها و Base
  entities.py      # تعریف مدل‌ها
```

محتوای مدل‌های واقعی را در `entities.py` قرار دهید و در `__init__.py` مدل‌ها را صریحاً export کنید. سپس بعد از اطمینان از انتقال کامل، فایل متداخل `models.py` را کنار بگذارید. تغییر فقط نام فایل بدون اصلاح importها کافی نیست.

### ب) رابطهٔ داکتر با حساب کاربری اشتباه است

در کد شما:

- `Prescription.doctor_id` به `doctors.id` اشاره می‌کند.
- `Prescription.doctor` به `Doctor` اشاره می‌کند.
- ولی سمت مقابل رابطه روی `User.prescriptions` تعریف شده است.
- `Doctor.prescriptions` اصلاً تعریف نشده است.
- همین اشتباه برای `Appointment` نیز تکرار شده است.

این کد الزاماً با `create_all()` تنها آشکار نمی‌شود؛ ساخت شیء یا query اولیه می‌تواند پیکربندی mapperها را فعال و اجرا را متوقف کند.

**اصلاح:** رابطه‌های نسخه و نوبت را روی `Doctor` قرار دهید:

```python
# در Doctor
prescriptions = relationship("Prescription", back_populates="doctor")
appointments = relationship("Appointment", back_populates="doctor")

# در Prescription
# doctor_id همچنان ForeignKey("doctors.id") است.
doctor = relationship("Doctor", back_populates="prescriptions")

# در Appointment
# doctor_id همچنان ForeignKey("doctors.id") است.
doctor = relationship("Doctor", back_populates="appointments")
```

رابطه‌های نادرست فعلی از `User` برداشته شوند. اگر هر داکتر حساب ورود دارد، ارتباط مستقل و مشخص `Doctor.user_id -> users.id` با قید یکتایی طراحی شود. شناسهٔ حساب کاربری و شناسهٔ داکتر را یکی فرض نکنید.

### ج) بیشتر routerها وجود ندارند

`main.py` دوازده router را import می‌کند، اما اسکریپت‌ها فقط `settings.py` و `auth.py` را تولید می‌کنند. موارد زیر ساخته نمی‌شوند:

```text
patients.py, doctors.py, appointments.py, prescriptions.py,
medicines.py, lab.py, radiology.py, admissions.py,
surgeries.py, invoices.py
```

**اصلاح:** این ماژول‌ها باید واقعاً ساخته شوند؛ هرکدام با schema، اعتبارسنجی، احراز هویت، مجوز نقش‌ها و عملیات دیتابیس. حذف importها یا ساخت router خالی فقط خطای import را پنهان می‌کند، قابلیت را نمی‌سازد.

### د) مسیر پروفایل شفاخانه توسط مسیر پویا گرفته می‌شود

در `settings.py`:

```python
@router.put("/{setting_id}")
# ...
@router.put("/hospital")
```

درخواست `PUT /hospital` ابتدا با مسیر پویا تطبیق می‌شود و تبدیل `hospital` به عدد شکست می‌خورد. این نقص برای **PUT** است؛ در نمونهٔ ارسالی، GET با چنین مسیر پویایی تعریف نشده است.

**اصلاح:** مسیر ثابت را پیش‌تر تعریف کنید؛ بهتر از آن، مسیرها را بدون برخورد طراحی کنید، مثلاً `/hospital` و `/entries/{setting_id}`. schema بدنهٔ درخواست نیز تعریف شود.

### هـ) بدنهٔ JSON با امضای API هماهنگ نیست

تعریف زیر به‌صورت پیش‌فرض پارامترهای query می‌خواهد:

```python
def login(email: str, password: str, db: Session = Depends(get_db)):
```

اگر frontend JSON بفرستد، پاسخ `422` می‌شود. این مسئله برای چند API تنظیمات و فعال‌سازی نیز وجود دارد.

**اصلاح:** از مدل Pydantic برای بدنه استفاده کنید و frontend را با همان قرارداد هماهنگ کنید. رمز نباید در URL/query قرار گیرد؛ URL ممکن است در لاگ و history ثبت شود. خطای 422 را با حذف اعتبارسنجی پنهان نکنید.

### و) انقضای سریال و timezone

SQLite در مسیر آزمایش‌شده حتی با `DateTime(timezone=True)` مقدار را بدون timezone برگرداند. مقایسه با `datetime.now(timezone.utc)` خطا داد.

**اصلاح:** قرارداد ذخیرهٔ UTC مشخص کنید. مقدارهای فاقد timezone فقط وقتی به UTC علامت‌گذاری شوند که معلوم باشد واقعاً UTC ذخیره شده‌اند؛ برای دادهٔ قدیمی با مبنای نامعلوم، تبدیل کورکورانه اشتباه است. `check-activation` نیز باید انقضا را بررسی کند، نه فقط `is_active` و `activated_at` را. منقضی‌شدن سریال نباید دسترسی ضروری به سوابق مریض را بدون سیاست ایمن قطع کند.

### ز) وابستگی دوری و مسیر دیتابیس

routerها `get_db` را از `main.py` می‌گیرند و `main.py` همان routerها را وارد می‌کند. این یک وابستگی دوری و شکننده است؛ لزوماً در ترتیب معمول startup فوراً خطا نمی‌دهد، ولی import مستقیم router، تست‌ها و seed می‌توانند مشکل پیدا کنند.

**اصلاح:** `engine`، `SessionLocal` و `get_db` در `backend/app/database.py` باشند. هیچ مدل، router یا seed برای گرفتن اتصال، `main.py` را import نکند. مسیر SQLite نسبت به مسیر مطلق ریشهٔ پروژه ساخته شود، نه پوشهٔ فعلی اجرای فرمان. فولدر داده پیش از اتصال ایجاد شود. مقدار `DATABASE_URL` واقعاً از تنظیمات خوانده شود.

## ۴. مشکلات امنیتی — پیش از هر دادهٔ واقعی اصلاح شود

1. **رمز متن ساده است.** نام ستون `password_hash` چیزی را hash نمی‌کند. ذخیره و مقایسهٔ مستقیم رمز ناامن است. Argon2id یا سازوکار معتبر password hashing لازم است. اعتبارنامه‌های نمونهٔ منتشرشده و کلید ثابت نمونه در استقرار واقعی استفاده نشوند.
2. **ورود، نشست معتبر ایجاد نمی‌کند.** پاسخ `success: true` بدون session/token و بدون بررسی در endpointهای بعدی، حفاظت ایجاد نمی‌کند. نشست server-side یا token دارای انقضا، خروج/ابطال، و حفاظت مناسب CSRF برای cookie لازم است. یک flag در `localStorage` کنترل دسترسی نیست.
3. **مجوز نقش‌ها وجود ندارد.** هر API مریض، نسخه، مالی و تنظیمات باید احراز هویت و مجوز مناسب داشته باشد. دسترسی بدون ورود باید `401` و نقش غیرمجاز باید `403` بگیرد.
4. **CORS باز همراه credentials مناسب نیست.** originهای مشخص و موردنیاز مجاز شوند. CORS جای احراز هویت را نمی‌گیرد.
5. **فایل `.env` عملاً در کد مصرف نشده است.** ساخت آن به‌تنهایی تنظیمات را تغییر نمی‌دهد. config باید با ابزار مناسب بارگذاری شود و کلید امن تولید شود؛ رازها در repository ثبت نشوند.
6. **وجود مدل AuditLog، ثبت رویداد نیست.** باید رویدادهای واقعی، کاربر، زمان و تغییرات مهم ثبت و از دستکاری محافظت شوند؛ رمز و اطلاعات حساس بی‌ضرورت وارد لاگ نشود.
7. **داده‌های مریض، upload و backup نیاز به حفاظت دارند.** محدودیت دسترسی، رمزگذاری مناسب، سیاست نگهداری و آزمون بازیابی لازم است. مسیر عمومی `/static` محل مناسب پروندهٔ مریض نیست.

## ۶. ملاحظات طبی بسیار مهم

- افزودن اجباری سیرم، ویال و دو آمپول به **همهٔ نسخه‌ها** نباید پیاده شود. این تصمیم باید ضرورت بالینی، وضعیت مریض و تأیید داکتر داشته باشد؛ شمار ثابت دوا معیار کیفیت نسخه نیست.
- سن، جنس و وزن به‌تنهایی برای دوز خودکار کافی نیستند. حساسیت، بارداری/شیردهی، عملکرد کلیه/کبد، شدت بیماری، راه مصرف، تداخلات، غلظت دارو و سقف دوز هم اهمیت دارند.
- نبود هشدار در دیتابیس سه‌جفتی به معنی نبود تداخل نیست. رابط باید صریحاً محدودیت پوشش را نشان دهد.
- تصحیح خودکار و بی‌خبر نام دوا یا دوز خطرناک است. پیشنهاد اصلاح باید با نام کامل، قدرت و شکل دوا نمایش داده و توسط داکتر تأیید شود؛ متن اولیه و انتخاب نهایی ثبت شوند.
- تولید خودکار تشخیص قطعی، نتیجهٔ معاینهٔ انجام‌نشده یا پروتکل عملیات برای ثبت در دوسیه مجاز و ایمن نیست. پیش‌نویس و دادهٔ تأییدشده باید از هم جدا باشند.
- BMI و حدود علایم حیاتی این نمونه، تصمیم‌یار جامع نیستند؛ ورودی صفر/منفی و گروه‌های سنی مختلف هم بررسی نشده‌اند.
- ادعای «۹ از ۱۰ دانش جهان» قابل سنجش نیست. معیار معتبر، پوشش مشخص، منبع دارای مجوز، تاریخ به‌روزرسانی، آزمون بالینی و نظارت متخصص است.

## ۷. نقشهٔ اصلاح، به ترتیب درست

### مرحلهٔ ۱ — بازیابی فایل‌های واقعی

از محیطی که ادعا شده برنامه در آن ساخته شده، فایل پروژه را export کنید. فایل‌های لازم شامل frontend، backend، اسکریپت‌ها، dependencyها و لوگو است؛ نه عکس صفحه و نه فایل حاوی رمز/اطلاعات مریضان. بدون این فایل‌ها، تعمیر برنامهٔ قبلی ممکن نیست.

### مرحلهٔ ۲ — ساخت backend قابل اجرا

1. تداخل `models` را برطرف کنید.
2. `database.py` و config مستقل بسازید.
3. رابطه‌های `Doctor`، `Prescription` و `Appointment` را اصلاح کنید.
4. routerهای مفقود و schemaها را پیاده کنید.
5. مسیر ثابت `/hospital` را از مسیر پویا جدا کنید.
6. migration، قیود یکتایی/مقادیر معتبر، transaction و rollback تعریف کنید. برای پول از `Numeric/Decimal` مناسب استفاده شود، نه تکیه بر Float.
7. import و پیکربندی mapperها را پیش از اجرا تست کنید.

### مرحلهٔ ۳ — امنیت و ذخیرهٔ واقعی

ابتدا hash رمز، session و نقش‌ها؛ سپس اتصال frontend به API. هر عملیات باید پس از refresh و restart قابل بازیابی باشد. دادهٔ نمایشی، localStorage و دادهٔ واقعی واضح از هم جدا شوند.

### مرحلهٔ ۴ — طراحی و چاپ

۲۰ layout مستقل با header سه‌بخشی، بخش مریض و معاینه، جدول دوا و footer قابل‌ویرایش تعریف شود. یک schema مشترک برای دادهٔ نسخه و یک renderer مشترک برای preview و چاپ لازم است تا نتیجهٔ چاپ از انتخاب قالب جدا نباشد. A4 دقیق `210 × 297 mm`، حاشیه، متن راست‌به‌چپ، نام انگلیسی دوا، فونت محلی، صفحه‌بندی و نسخهٔ طولانی روی چاپ واقعی آزمایش شود. طرح تیرهٔ پرمصرف باید گزینه باشد، نه اجبار.

### مرحلهٔ ۵ — پشتیبان‌گیری و بستهٔ آفلاین

از SQLite زنده با روش سازگار مثل SQLite backup API نسخه بگیرید؛ کپی خام فایل در حال نوشتن می‌تواند ناقص باشد. فایل‌های ضمیمه و نسخهٔ schema نیز لحاظ شوند. restore روی یک محیط جداگانه انجام شود؛ تا بازیابی موفق آزمایش نشده، backup معتبر فرض نشود.

برای آفلاین باید ابتدا مشخص شود «همهٔ قابلیت‌ها» دقیقاً چیست. سرویس ابری بدون شبکه آفلاین کار نمی‌کند؛ قابلیت AI محلی نیاز به مدل، سخت‌افزار، مجوز و اعتبارسنجی مستقل دارد. dependencyهای Python برای نسخه و معماری ویندوز هدف، فونت‌ها، assetها و راهنمای نصب باید بسته‌بندی شوند؛ سرور محلی همچنان لازم است. نصب روی یک کمپیوتر تمیز و قطع اینترنت آزمایش شود.

## ۸. فرمان‌های ویندوز — فقط پس از موجودبودن و اصلاح فایل‌ها

این‌ها درمان خودکار کد فعلی نیستند. ابتدا PowerShell را در پوشهٔ واقعی پروژه باز کنید؛ پیش از تغییر هر فایل موجود، نسخهٔ پشتیبان بگیرید. فرض نکنید درایو E موجود است.

```powershell
Get-Location
Get-Command python
Get-ChildItem
Test-Path .\requirements.txt
Test-Path .\backend\app\main.py
Test-Path .\frontend\js\app.js
```

پس از اصلاح ساختار و موجودبودن فایل‌ها:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -c "from backend.app.models import Base; from sqlalchemy.orm import configure_mappers; configure_mappers(); print('Models OK')"
```

اجرای seed فقط پس از استقلال اتصال دیتابیس از main و ایجاد schema:

```powershell
.\.venv\Scripts\python.exe -m scripts.seed_data
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

اجرای `-m scripts.seed_data` از ریشه، مشکل رایج پیدا نکردن پکیج `backend` در اجرای مستقیم `python scripts/seed_data.py` را دور می‌زند. seed باید تکرارپذیر و غیرمخرب باشد و دادهٔ نمونه را با دادهٔ واقعی مخلوط نکند.

در پنجرهٔ دیگر:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/healthz
Start-Process http://127.0.0.1:8000/docs
```

`127.0.0.1` برای استفادهٔ همان کمپیوتر ویندوز است. برای preview میزبانی‌شده یا شبکهٔ داخلی، binding، proxy، firewall و origin باید جدا تنظیم شود؛ آدرس localhost در مرورگر کاربر به سرویس راه‌دور اشاره نمی‌کند. برای استفادهٔ واقعی، `--reload` و سرور توسعه انتخاب استقرار نیستند.

در اسکریپت‌های نصب، `$ErrorActionPreference = 'Stop'` و بررسی نتیجه لازم است. برای دستورهای خارجی مثل Python، `$LASTEXITCODE` نیز صریح بررسی شود؛ چاپ `Ready` پس از یک فرمان شکست‌خورده نباید ممکن باشد. تغییر سراسری ExecutionPolicy به `Unrestricted` راه‌حل توصیه‌شده نیست.

## ۹. آزمایش‌هایی که واقعاً در این بررسی اجرا شدند

فایل `tests/audit/test_supplied_examples.py` شامل **۷ آزمایش مستقل حداقلی** است. این فایل از روی الگوهای کد ارسالی ساخته شده، نه از برنامهٔ کامل مفقود:

1. تقدم پکیج `models` و شکست import فایل هم‌نام — بازتولید شد.
2. `NoForeignKeysError` برای رابطهٔ User/Prescription — بازتولید شد.
3. نمونهٔ اصلاح‌شدهٔ رابطه روی Doctor — پیکربندی موفق بود.
4. `422` برای PUT پروفایل به علت ترتیب مسیرها — بازتولید شد.
5. ثبت مسیر ثابت پیش از مسیر پویا — نمونهٔ حداقلی پاسخ 200 داد.
6. `422` برای JSON در login با پارامتر scalar — بازتولید شد.
7. حذف timezone در رفت‌وبرگشت SQLite و `TypeError` مقایسه — بازتولید شد.

**نتیجه: ۷ از ۷ تست بازتولید/نمونهٔ اصلاحی گذشت.** گذشتن این تست‌ها به معنی سالم‌بودن سیستم شفاخانه نیست؛ چند تست عمداً وقوع خطا را انتظار دارند. PowerShell روی ویندوز، نصب کامل ده اسکریپت، frontend، چاپ و جریان واقعی مریض در این محیط آزمایش نشده‌اند.

برای اجرای مستقل تست‌ها با Python 3.11:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r tests/audit/requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests/audit -v
```

محیط بررسی: Python 3.11.2، FastAPI 0.120.0، SQLAlchemy 2.0.44، HTTPX 0.28.1. تمام dependencyهای اسکریپت اصلی با هم نصب نشده‌اند؛ این آزمایش‌ها بررسی سازگاری کامل requirements اصلی نیستند.

## ۱۰. شرط اعلام «آمادهٔ استفاده»

- نصب موفق از صفر روی سیستم هدف و اجرای تست‌های یکپارچه.
- عدم دسترسی به اطلاعات مریض بدون مجوز.
- ثبت و بازیابی مریض، نسخه، نتیجهٔ لابراتوار و پرداخت پس از restart.
- عدم تکرار شناسه‌ها، جلوگیری از موجودی منفی و ثبت مالی معتبر.
- چاپ A4 واقعی با ۲۰ layout و اطلاعات ثابت و صحیح.
- backup و restore آزمایش‌شده.
- محدودیت روشن دستیار طبی، منابع معتبر و تأیید داکتر.
- استفاده از دادهٔ آزمایشی تا پایان تأیید امنیتی و بالینی.

**قدم بعدی:** فایل‌های واقعی پروژه یا traceback اولین اجرای ناموفق را بدون راز و بدون اطلاعات مریضان فراهم کنید. در وضعیت فعلی می‌توان ایرادهای کد ارسالی را اثبات کرد؛ اما نمی‌توان صادقانه گفت برنامهٔ قبلی تعمیر و تکمیل شده است.
